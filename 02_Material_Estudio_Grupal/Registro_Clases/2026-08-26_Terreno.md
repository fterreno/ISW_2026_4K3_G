# Estimaciones de Software
Una estimación de software tiene que ver con la predicción de algo que puede pasar en el futuro. Está directamente relacionada con el nivel de incertidumbre que manejamos en el momento de hacer la predicción. Cuando comienza un proyecto existe un nivel de incertidumbre alto porque todavía no conocemos completamente lo que va a suceder. A medida que el proyecto avanza, obtenemos más información y, por lo tanto, el nivel de incertidumbre debería disminuir. Por este motivo, las estimaciones pueden cambiar a lo largo del proyecto.

La estimación, por definición, no es precisa. Es una predicción basada en la información que tenemos en un determinado momento. Por eso, la actividad de estimar no se realiza una única vez, sino que se realiza a lo largo de toda la vida del proyecto. El equipo toma decisiones en función de las estimaciones disponibles en cada momento y estas estimaciones deberían actualizarse a medida que aparecen nuevos datos y se conoce mejor el proyecto.

La estimación no es el plan.

El plan representa el compromiso que tenemos con el negocio. La estimación es una predicción que nos permite conocer con qué cosas nos podríamos comprometer y sirve como una de las bases para construir el plan, pero el plan no debe ser lo mismo que lo estimado. La estimación responde a la pregunta de qué creemos que puede ocurrir, mientras que el plan representa el compromiso que asumimos teniendo en cuenta, entre otras cosas, las estimaciones disponibles.

Las estimaciones no son un plan ni un compromiso. Una estimación permite conocer con qué cosas nos podríamos comprometer, pero no representa por sí misma un compromiso con el negocio. Las estimaciones son una base para construir los planes, pero los planes no deben confundirse con lo estimado. Al comienzo del proyecto las estimaciones poseen mucha incertidumbre y, a medida que el proyecto avanza y se obtiene nueva información, el nivel de incertidumbre debería disminuir. Por esta razón, es normal que una estimación sea revisada y modificada durante el desarrollo del proyecto.

La actividad de estimar se realiza durante toda la vida del proyecto y el equipo toma decisiones en base a estas estimaciones. La estimación no debe entenderse como un valor definitivo, sino como una predicción que tiene sentido en el momento en que se realiza y que puede mejorar cuando contamos con mayor conocimiento sobre el proyecto.

La estimación es una predicción de lo que podría ocurrir en el futuro, mientras que el plan es el compromiso que asumimos con el negocio teniendo en cuenta, entre otras cosas, las estimaciones disponibles. La estimación nos ayuda a construir el plan, pero una estimación no se convierte automáticamente en un compromiso.

## Errores de Estimacion

Los errores de estimación pueden venir de utilizar técnicas incorrectas, de no ajustar las estimaciones en base a los valores reales obtenidos o de utilizar una única técnica de estimación. También pueden generarse cuando nos basamos demasiado en información subjetiva o cuando utilizamos datos históricos que no son realmente comparables con el proyecto actual. Otro problema es no tener en cuenta el nivel de incertidumbre existente al momento de realizar la estimación.

Por este motivo, una estimación no debería considerarse como algo exacto o definitivo. Es necesario revisar las estimaciones a medida que se obtiene información real del proyecto y, cuando sea necesario, utilizar diferentes técnicas para reducir la dependencia de una única fuente de información o de un único criterio.

## Tecnicas de Estimacion
La técnica fundamental de estimar es contar. A partir de esta idea existen diferentes métodos que permiten realizar estimaciones. Algunos están basados en la experiencia, otros en comparativas de mercado y otros en los componentes que forman parte del producto.

Algunos metodos utilizados para estimar pueden ser:

- Metodos basados en la experiencia
- Metodos basados en las comparativas de mercado
- Metodos basados en los compoentes del producto

### Metodos basados en la experiencia
- Datos historicos
- Juicio Experto
    - Puro
    - Delphi
- Analigia

Dentro de los métodos basados en la experiencia se encuentran los datos históricos, el juicio experto y la analogía. En el caso del juicio experto podemos encontrar el juicio experto puro y el método Delphi.

Como es un a medida con alta incertidumbre, usualmente se hace una estimacion con rangos o porcentajes (no de un unico valor absoluto) pero si utilizamos unidades de medidas absolutas (ej. horas).

### Metodos Basados en la Experiencia: Datos Historicos

Se utiliza informacion existente para poder realizar estimaciones relacionadas con un nuevo proyecto.

Las dificultades que se pueden llegar es que los datos sean subjetivos (la experiencia no siempre es extrapolable).

Los datos historicos se deberian guardar en un almacenamiento para que estos mismos me sirvan. Necesito un registro del dato historico para poder utilizarlo. Es dificil almacenar este tipo de informacion para luego poder utilizarlo y compararlo con el nuevo proyecto. Es dificil almacenarlo de forma tipificada para poder comparar los datos con otro proyecto.
Es dificil tambien determinar que datos tienen valor para utilizarlo a futuro.

### Metodos Basados en la Experiencia: Juicio Experto Puro

Existe una persona que conoce del tema, ue estudia las caracteristicas y especificaciones del proyecto, y es esta persona quien realiza la estimacion.
Una de las dificultades es que el proyecto depende demaciado de este mismo experto. Es subjetivo. Si el experto no realiza la tarea entonces es dificil estructurar este juicio. En la practica es la tecnica más utilizada.

El juicio del experto se estructura:
- Desglozar las tareas en una granularidad aceptable
- Se utilzia una formula utilizando el metodo de "optimista, persimista y habitual". No es una formula matematica exacta pero si ayuda para un buen comienzo.

### Metodos Basados en la Experiencia: Juicio Experto Delphi
La estimacion se hace grupal bajo la premisa que las estimaciones grupales son mas importantes que las individales.
El metodo se basa en un conseso entre los jueces expertos. Las estimaciones se hacen individuales, cada experto expone su estimacion, y se repite el ciclo hasta llegar a un rango aceptable.

## Estimaciones Agiles
En las estimaciones agiles se utilizan la unidad de medida llamada Story Points, es una unidad relativa que solo tiene valor para las personas que trabajan en el proyecto. No es una medida basada en el tiempo sino es basada en el tamaño. Es relativa porque surge de la comparacion.

Las estimaciones en agil se hacen a nivel grupal.

El "tamaño", en este contexto, es cuando grande o pequeño es algo. El tamaño indica la complijidad, cuanto trabajo es requerido para ahcer o completar la user story y cuan grande es la user story, cuanto es lo que no sabemos de lo que intentamos construir en la user story.

Existe una diferencia entre la descripcion de un trabajo que hay que hacer y el esfuerzo de hacerlo.

Las estimaciones agiles tienen las siguientes definiciones:
- Elegimos una escala, cualquiera, una vez elejida la escala se trabaja siempre con esta.
- Utilizamos el concepto de Story Point. Dependiendo de la complejidad, lo que no se de la user story (incertidumbre) y el esfuerzo que toma resolverla genera el "peso" de la user story, el story point.

## Planning Poker
Inspirado en Juicio Experto Delphi.
Tiene reglas:
- Quienes estiman es quien realiza la tarea.
- Se utiliza la serie de Fibonacci. No se debe superar 8 story points. La escala es la siguiente 0; 0.5; 1; 2; 3; 5; 8.

Cuando se hace la estimacion se le asigna a las user story se le asigna una medida relativa.

En un inicio, como equipo, se elije una user story sencilla, lo suficiemtemente facil para asignarle un pero de cero. Se denomina user story canonica, a partir de esta user story canonica se estima las proximas user story.

Ej. para la user story 1, vale el doble de lo que seria hacer la user story canonica, po lo que se le pone de peso 2.

Prerequisistos
- Lista de user storys a ser estimadas
- Cada estimador tiene el "mazo de cartas".

Pasos:
- Se determina la user story canonica, que sera utilizada para comparar con las otras user storys. Se pone de acuerdo el equipo para asignarle un valor de "1 story point". Esta user story canonica no se puede modificar a lo largo del desarrollo del proyecto.
- La user story a ser estimada se lee ea todo el equipo.
- Los estimadores discuten la user story (se lehacen preguntas al product ownser, etc)
- Cada estimador selecciona una carta con el valor de estimacion que el mismo eligio, una vez todos eligieron la carta y se exponen al mismo tiempo.
- Los estimadores que se encuentran en los limites superior e inferior de la escala exponen su punto.
- Se repite el ciclo hasta que todos esten de acuerdo con el peso de la user story.

# Gestion de Producto

Validacion de la hipoteasis de que lo que se construye realmente va a ser de valor. Luego una vez validada la hispotesis se define el aclance, pasa por el diseño hasta la experiencia de usuario.

Uusalmente se pasa mucho timepo que se crean funcionalidad es que poco se utilizan, genera un desperdicio. Lo que se necesita es optimizar las funcionalidades que SIEMPRE se utilizan. Escribir codigo y crear valor no es lo mismo.

Se debe tener como objetivo crear un producto de software que le de valor al cliente.

Se debe tener en cuenta que, al crear un producto de software, este resuelva el problema que nosotros como desarrolladores queremos que resuelva y que este producto le brinde al usuario una experiencia que haga querer al usuario volver a querer utilizar este producto software.

## Cronologia de Lanzamiento: Ecosistema de los Minimos
### Producto Minimo Viable (MVP)
A partir de una propuesta de un software que puede ser aceptado en el mercado, se genera un producto pequeño que nos permita validar que este producto realmente le genera valor al mercado. Se debe generar con el menor de los esfuerzos porque existe unicamente para confirmar la hipotesis del producto, una vez se valida la hipotesis se le dan mas recursos.

Pero para el usuario la experiencia no deberia cambiar, para nosotros como desarrolladores si lo notamos per la experiencia de usuario si es la misma.

**Su intencion es validar una hipotesis en el mercado.**

Existe a su vez el dilema del lanzamiento, el costo del retraso, al audacia de cero (cero cliente sy cero ingresos, me arriezgo porque espero que el producto tiene mucho para ofrecer). COn el MVP es validar la hipotesis de que lo que se esta creando va a tener un publico y va a brindar valor al cliente.

Para el usuario debe ser un producto que ya esta funcionando.

Una vez tenemos un MVP y lo pivotamos a un MVP2, una vez nos genera valor debemos empezar a pesar en el:

### Producto MInimo VIable (MMF)
Un producto ya comercializable, que se lo puede liberar y que genere valor. Tenemos una evolucion del MVP a un minimo producto ocomercializable. Y a medida que ya poseemos el MVF podemos iniciar haciendo pruebas de valor, hipotesis, con caracteristicas que se le pueden agregar y a esto se le llama:

### Minima Feature Viable (MVF)

Todos estos tres, MVP, MMF y MVF son atomicos. La palabra minimo no significa "pequeño", no esta relacionado con las dimienciones que tiene el producto sino que son las funciones minimas necesarias. El producto puede ser algo complejo y grande.
